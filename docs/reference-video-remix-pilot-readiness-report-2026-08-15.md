## 1. 执行结论

当前可以完整验收**这条视频的最终成片**，但不能验收“整个优化计划已经完成”，也不具备直接向一线运营开放 V2 Skill 的条件。

| 验收层级 | 当前判定 | 说明 |
| --- | --- | --- |
| 单条成片 Gate 5 | **通过** | 用户已确认最终预览；媒体、时间轴、素材和哈希硬校验通过 |
| 替代 G-A pilot | **不通过** | 存在审批时间线倒置、真实任务状态未接入 Fast Path、返工审批依赖一次性脚本等审计缺口 |

| Track B 生产执行器 | **未完成** | 真实任务仍依靠任务目录内一次性脚本，状态、缓存、续跑、指标未统一 |

因此，最准确的项目状态是：**成片成功，方法得到部分验证；流程产品化和规模化生产尚未完成。**

## 2. 为什么成片仍在 `work/`

这不是遗漏，而是当前契约的明确要求。本任务是 `manual-contract-only` V2 alpha pilot，只用于采集 G-A 前向证据。即使 Gate 5 通过，也不得迁移到 `final/`、不得作为普通生产发布、不得复用任何审批。

`final/` 只接收已获得生产资格的普通任务。当前 pilot 留在 `work/`，能够保留全部审核包、中间版本、返工记录和审批证据，是正确状态。

## 4. 流程上已经发生的有效变化

相较旧流程，本次 pilot 已实际验证以下设计价值：

1. **参考事实和目标结构分离。** `recipe.json` 保留参考事实，目标删并段进入 Blueprint，不再因新配音回写参考事实。
2. **Gate 2 原子批准。** Blueprint、内容基线、声明边界、fallback 和时长包络被作为同一内容契约确认。
3. **Gate 3 拆成两个子状态。** 先确认素材和宽范围，再做逐句证据闭环，避免只有“画面相似”却无法支持文案。
4. **宽范围和精确裁点分离。** Gate 3 批准宽范围；真实 TTS 后，Reconstruction 只在批准范围内收窄精确裁点。
5. **新视频时长由完整实现 Blueprint 和真实配音决定。** 最终接受 27.936 秒，而不是把画面强压回参考片或 11–18 秒软包络。
6. **音频边界得到真实修复。** PCM 拼接替代 MP3 流级拼接，修复片段边界后重新完成 Gate 4 生成后听审。
7. **最终产物有哈希闭环。** MP4、校验报告、渲染报告和导入清单均绑定到 Gate 5 决定。

这些变化提升了可解释性和最终稳定性，尤其解决了“真实配音出现后才被迫全面重做镜头”的主要结构问题。

## 5. 为什么替代 G-A 仍不能判定通过

### 5.1 审批时间线不可审计

Gate 3 范围扩展记录为 `12:35`，但声称绑定扩展输入的 Gate 4 生成前重新批准记录为 `12:20`。后置输入不能由更早的决定授权。最终 Gate 5 接受成片不能追溯修复上游审批顺序。

### 5.2 真实任务尚未接入 Fast Path 状态契约

对本任务执行只读 `audit` 的当前结果为：

```json
{
  "status": "failed",
  "errors": ["unsupported execution_mode"],
  "execution_mode": null,
  "state_revision": null,
  "event_count": 0
}
```

这说明 `pipeline_state.json` 虽然记录了 Gate 决定，但还不具备统一执行器要求的运行模式、单调 revision 和事件审计链。

### 5.3 返工仍依赖任务专用脚本

任务根目录包含 22 个 `.mjs/.py` 一次性脚本，覆盖切分、规划、匹配、范围扩展、TTS、时间轴修复、遮盖策略变更、渲染和审批。它们能完成这一个案例，但不能形成一线人员可重复调用的 Skill 能力。

尤其最后两次叠字策略调整，是先产生任务专用产物，再用专用脚本绑定审批。标准流程应是：

```text
生成当前审核包
→ 展示业务变化、预览和输入哈希
→ 用户批准当前审核包
→ 统一 Gate 命令原子推进状态
→ 只重算受影响下游
```

当前证据不足以证明这条链路在真实任务中成立。因此，替代 pilot 应形成新的 G-A 评估，结论为 `not_passed`，不能沿用只覆盖旧 pilot 的现有 G-A 文档。

## 6. 效率变化与一小时目标

### 6.1 本次实测

| 时间点 | 时间 |
| --- | --- |
| Brief 批准 | 11:00:59 |
| Gate 1 批准 | 11:15:32 |
| Gate 2 批准 | 11:32:58 |
| 首次 Gate 3 选材批准 | 12:00:00 |
| Gate 3 证据闭环批准 | 12:10:00 |
| 最终 Gate 4 生成后批准 | 13:18:00 |
| Gate 5 批准 | 17:45:00 |

Brief 到 Gate 5 的墙钟时间约 **6 小时 44 分**；最终 Gate 4 生成后到 Gate 5 仍约 **4 小时 27 分**。后半段主要消耗在叠字/遮盖方案的多轮视觉返工，而不是正式 FFmpeg 渲染本身。

本次没有完整记录 `machine_seconds`、`api_seconds`、`operator_touch_seconds`、`human_wait_seconds`、`rework_seconds` 和缓存命中，因此不能计算真正的机器关键路径，也不能把 6 小时 44 分全部归因于系统。

### 6.2 已有提速能力的真实边界

Fast Path v0 当前 75/75 测试通过，已验证原子状态写入、Gate 停止、续跑、缓存失效、素材技术索引和审计规则。它证明“执行器底座可行”，但尚未接入本次真实五阶段命令，因此不能用该测试宣称真实生产已提速。

计划中的两个指标必须分开验收：

| 指标 | 建议定义 | 当前状态 |
| --- | --- | --- |
| 系统关键路径 SLA | 冷启动 ≤13 分钟；热缓存 ≤8 分钟；排除人工 Gate 等待 | 未实测 |
| 一线端到端 SLA | 素材合格、外部 API 正常、运营及时审核时，60 分钟内 Gate 5 可审 | 未达到/未验证 |

要实现一小时，不能靠减少 Gate，而应消除重复全量计算和晚期业务决策。叠字/水印/字幕策略必须前置到 Gate 3；一次性脚本必须收敛为可缓存命令；每个 Gate 的审核内容必须压缩为运营能在数分钟内判断的预览包。

## 7. 效果上的变化

### 7.1 已证实的改善

- 素材覆盖从“有文件可用”提升为“11 个叙事 fragment 均有获批素材和证据范围”。
- 文案与画面从松散对应提升为逐句证据闭环，保障条款被单独要求完整可读。
- 真实配音时长成为画面和字幕的时间权威，字幕、音频和镜头累计时间轴闭合。
- 精确裁点不越过 Gate 3 批准素材范围，避免静帧硬拉和未授权变速。
- 多次返工产物被保留，没有覆盖最终证据，最终输出具备可追溯哈希。

### 7.2 尚未量化的部分

- 开头三秒钩子是否优于旧流程；
- 参考爆款叙事结构的保真度和业务适配度；
- 素材匹配的语义、动作、构图、产品可见度和连续性分数；
- 声明可信度、字幕可读性和品牌洁净度的自动评分；
- 相同冻结输入下 V1/V2 的盲评差异；
- 多案例的首轮通过率与返工率。

这些应由 G-B 的冻结案例配对和后续 Track C 评分补齐，而不是用本次 Gate 5 人工通过代替。

## 8. 集成进 Skill 并向一线开放前的优化

### P0：先获得可重复、可审计的生产后端

#### 8.1 重跑一个干净 G-A pilot

- 从 Stage 0 使用冻结输入重新运行，不复用任何旧批准；
- 预先固定“上下均不遮盖”的叠字策略；
- 所有 Gate 只通过统一命令记录，严格保证审核包先生成、批准后推进；
- 自动校验时间单调、输入哈希、stale 传播和子状态完整性；
- 产出新的替代 G-A 正式评估，owner 明确批准后才解锁 Track B。

#### 8.2 把真实五阶段固化为通用命令

至少提供以下稳定入口，禁止在任务目录生成执行源码：

```text
init / precheck
split-reference
build-blueprint
build-mutation-plan
index-assets / match-assets
approve-gate
materialize-approved-broad
build-evidence-matrix / compile-script
generate-voice / build-timeline
render-final / validate / status / audit / resume
```

每个命令都必须声明输入、输出、缓存键、最早所需 Gate、失败恢复点和退出码。

#### 8.3 统一状态、审批和事件

`pipeline_state.json` 增加并强制校验：

- `execution_mode`、`run_id`、单调 `state_revision`；
- 工作状态与 Gate 审批状态分离；
- `pipeline_events.jsonl` 单调事件序列；
- 当前审核包哈希绑定的结构化 Gate 决定；
- 上游变化自动使受影响 Gate 和下游产物 `stale`；
- staging、原子提升、失败恢复和并发锁；
- 完整 artifact shape validator，而不只检查共同 envelope。

#### 8.4 前置高返工业务决策

Gate 3 每个素材候选必须显式选择：`保留原字 / 裁切 / 遮盖 / 替换 / 无处理`。审核包同时展示开头三秒、产品主体、上下文字区、声明卡、保障条款和 CTA 的代表帧或短代理视频。

这一步应在正式配音和渲染前完成。策略变化只使受影响的匹配、代理和渲染节点失效，不重跑参考拆解、Blueprint 或无关素材。

#### 8.5 建立可验收的效率数据

每次 attempt 写入：

- 机器执行、外部 API、运营操作、人工等待和返工时间；
- 缓存命中、重试、失败原因、Gate 返回次数；
- 首次可审时间、首次通过时间、最终通过时间；
- 返工原因分类：素材、结构、文案、声音、字幕、叠字、渲染。

G-B 使用同一冻结案例完成 V1/V2 冷启动和热缓存配对。只有真实五阶段达到质量不回退、冷启动 ≤13 分钟、热缓存 ≤8 分钟，才可进入 `2.0.0-rc.1`。

### P1：把后端能力包装成一线工作台

#### 8.6 FastAPI + SSE 作为标准后端界面

- FastAPI 只读取同一权威状态，不维护第二套状态机；
- SSE 只通知 revision 变化，前端再拉取当前快照；
- 首版提供任务列表、任务详情、当前 Gate、阻塞、最近活动、审核包和媒体预览；
- 路径、媒体和项目 ID 必须 allowlist，默认只绑定 `127.0.0.1`；
- Gate 写操作等统一审批命令稳定后再开放，不让前端直接改 JSON。

#### 8.7 Backlot 式运营表达

前端用业务语言投影五阶段和 Gate，例如：

```text
检查任务资料
→ 拆解参考视频
→ 确认复刻结构
→ 匹配并确认素材
→ 生成并试听配音
→ 合成与质检
→ 查看最终成片
```

状态只显示“系统处理中、待你确认、已确认、需重新确认、阻塞、失败、完成”。进度来自状态和真实计数，不使用虚假的线性百分比或 ETA。OpenMontage Backlot 只借鉴交互布局；因其为 AGPL-3.0，不复制代码、样式、资源或数据模型。

#### 8.8 一线默认策略和异常处理

- 提供标准 Brief、素材提交规范和业务镜头标签词典；
- 默认展示缺素材和低置信度，不用无关素材凑数；
- 素材缺口先建议补拍/补图；需要删并段或改变声明时明确返回 Gate 2；
- 为常见品类提供钩子、证明、使用动作、细节、生活方式、声明证据和 CTA 模板，但不把模板当成事实；
- 支持从最后有效阶段续跑，禁止运营通过重复点击制造多个并发任务；
- 任何失败都给出“发生了什么、对成片的影响、需要运营做什么、可从哪里继续”。

## 9. 一线开放的分级建议

| 阶段 | 可用人群 | 准入条件 | 当前是否达到 |
| --- | --- | --- | --- |
| 内部研发 pilot | 开发/流程 owner | 单条逐 Gate 运行，可人工修复 | 是 |
| 运营陪跑试用 | 受训运营 + 技术值守 | G-A 通过；真实执行器和统一审批入口完成；3 个冻结案例无越权 | 否 |
| 小范围一线试用 | 指定品类运营 | G-B 通过；≥10 条任务，首轮通过率、返工率和 SLA 有实测 | 否 |
| 普通生产开放 | 一线运营 | Track C 基础质量门禁、监控、回滚和版本发布批准 | 否 |

建议不要从当前 alpha 直接跳到全量开放。先用单一品类、素材较完整、声明风险较低的任务做陪跑；形成稳定数据后再扩大品类和人员范围。

## 10. 推荐的下一阶段顺序

1. **补发本次替代 pilot 的 G-A 评估**：正式记录 `not_passed` 和三个证据缺口。
2. **实现统一状态与 `approve-gate` 入口**：先解决审批可追溯和 stale 传播。
3. **把 22 个任务脚本收敛为 Skill 内通用阶段命令**：优先拆解、Blueprint、匹配、TTS/时间轴和渲染。
4. **以最终无遮盖策略重跑干净 G-A**：验证不再出现审批倒序或任务专用授权脚本。
5. **运行 G-B 冻结案例配对**：实测 13/8 分钟机器 SLA、质量不回退和返工变化。
6. **实现 FastAPI + SSE，再接 Backlot 式只读界面**：后端状态稳定后才做运营展示。
7. **以陪跑方式开放**：至少 10 条同品类任务收集首轮通过率、端到端时长和异常分布，再决定扩大范围。

## 11. 最终验收口径

本轮可以签署的结论是：

> `tablemat-ga-replacement-pilot` 的 27.936 秒最终视频已通过 Gate 5，媒体与时间轴硬校验通过，作为 pilot 正确保留在 `work/`。该结果证明五阶段方案能够产出可接受成片，但由于审批时间线、真实状态契约和通用执行入口仍不完整，替代 G-A、整个优化计划、一小时 SLA 和一线运营发布资格均未通过验收。

下一阶段的核心不是继续修这条 MP4，也不是先做前端，而是把这次人工成功路径变成**可重复、可审计、可缓存、可测量**的 Skill 后端，再用干净 pilot 和冻结案例完成 G-A/G-B 验证。
